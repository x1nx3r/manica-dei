## 2. Where the external calls actually hid

The PLAN named Sentry, the UI proxy, upgrade checks, stats/share,
console/identity. Grep found more, all removed:

- `packages/app/src/context/highlights.tsx` fetched
  `opencode.ai/changelog.json` at runtime for a release-notes popup —
  a whole feature (context + dialog + two settings rows) hanging off one
  URL constant. The settings key `releaseNotes` had to go with it.
- `entry.tsx` pulled the notification icon from an opencode.ai CDN URL
  and special-cased `location.hostname.includes("opencode.ai")` as a dev
  fallback. Both gone; icons are same-origin now.
- `session/retry.ts` carried Go upsell actions with links on provider
  errors; the app had matching upsell dialogs
  (`usage-exceeded-dialogs.tsx` + `dialog-usage-exceeded.tsx`).
- `installation/index.ts` fetched opencode.ai/install, npm/brew/choco/
  scoop registries, and the GitHub releases API to compute "latest".
- `packages/script` fetched the upstream npm registry to *derive the
  product's own version* (§5).
- `cli/cmd/github.handler.ts` called `api.opencode.ai` (the GitHub agent
  integration).

Lesson: grep the five obvious words, then read every `fetch(`/`http` call
in the two shipped packages. The marketing surfaces (Zen connect copy,
unpaid-model dialogs, featured-provider lists) carried as many external
URLs as the infrastructure did.

## 3. Share: the guard, the wrapper, the test

`SessionShare.create` wraps session creation
(`handlers/session.ts:155`), so **every `POST /session` passes through
share code** even when sharing is off. That is why the default matters
more than the endpoints: with `share: "auto"` or `OPENCODE_AUTO_SHARE`,
each new session streams its transcript to a hosted share service.

- The guard is now `OPENCODE_ENABLE_SHARE` (default off), read **lazily
  at call time** — the original module-load `const disabled` captured env
  at import, which makes the flag untestable from bun:test (single
  process; imports run before test bodies).
- `test/share/share-next.test.ts` sets the env at module scope to opt in.
- The full excision (module, endpoints, `SessionShareTable` migration)
  waits for the trimming avenue; the template entrypoint bakes
  `OPENCODE_DISABLE_SHARE=true` as a deployment-level second lock.

## 4. The upgrade surface was a tree, not a switch

Removing "the upgrade check" meant: `/global/upgrade` endpoint +
schema in `groups/global.ts`, the `GlobalHttpApi.upgrade` handler, the
`upgrade` CLI command + `cli/upgrade.ts`, `Installation.latest/upgrade`
(plus brew/choco/scoop specifics), the TUI `checkUpgrade` RPC and its
call site, and `Installation.Event` publish points. `Installation.method`
survives for `opencode uninstall`. `packages/script` also hard-read
`.github/TEAM_MEMBERS` — the build fails if that file is missing (§6).

## 5. Version identity phoned home

`packages/script/src/index.ts` fetched
`registry.npmjs.org/opencode-ai/latest` and bumped — the product's
version was derived from the upstream package. Now: manifest version
(`0.1.0`) or `OPENCODE_VERSION` env; channel `latest` unless overridden;
release CI passes the tag. The binary gets it as the `OPENCODE_VERSION`
build define (core `installation/version.ts`).

## 6. Removing a workspace dep (catalog + lockfile mechanics)

To drop a dependency in this monorepo: remove it from the package's
`package.json`, from the root `package.json` **catalog** (entries survive
otherwise and resolution fails with `failed to resolve`), then
`bun install` from the repo **root** — running it from a package dir
delegates but reports "no changes" misleadingly. Verify pruning with
`grep -c "@sentry" bun.lock` → 0. Desktop carried Sentry too; both app
and desktop had identical plugin/init patterns.

## 7. The drizzle baseline (RESOLVED 2026-10-01)

`bun typecheck` (turbo, all packages) failed with ~598 errors in
`packages/opencode`: type-identity clashes between drizzle-orm instances.
Root cause, established by experiment:

- Bun keys each `node_modules/.bun/<pkg>@<ver>+<hash>` copy by the
  package's **peer context** — which optional peers are installed in that
  chain. drizzle-orm has ~30 optional peers, so the workspace had four
  copies: `effect+otel+zod` (core, opencode), `effect` only
  (effect-drizzle-sqlite, server, desktop), plus two context instances
  nobody's symlink reached.
- The opencode typecheck program spans packages (workspace imports pull
  in core, server, and tui sources), so types flowing from
  `@opencode-ai/effect-drizzle-sqlite` (effect-only instance) clashed
  with core's own drizzle types inside core's own files.
- Not bun-version-related: 1.3.1, 1.3.14, and 1.4.2 all fork identically
  (1.4.2's installer also crawls at 98% CPU for 10+ minutes on a full
  fresh install here — avoid for installs).

**Fix**: declare the two missing optional peers (`zod`, `@opentelemetry/api`)
as devDependencies of the light packages
(`effect-drizzle-sqlite`, `server`, `desktop`) so every drizzle consumer
shares one peer context and one instance (`5716561`). Drizzle errors:
598 → 0. Lesson: in a bun workspace with peer-heavy packages, "who
resolves which instance" is a function of each consumer's optional-peer
set; when types cross package boundaries, align the contexts, don't
fight the types.

App typecheck was never affected (`tsgo -b` — a different config graph).

## 8. Bun version discipline

- Bun 1.3.1 **segfaults mid-suite** on this machine (SIGILL, ACP tests;
  the crashing file passes alone). Also 1.3.14 locally — but only when
  the suite is launched via `bun run test`, because the package script
  re-invokes `bun` and resolves **system** bun from PATH. Call the binary
  directly: `/tmp/opencode/bun-dir/bin/bun test …`. Under 1.3.14 the full
  suite completes locally (595 s) — CI on 1.3.14 is green apart from §13.
- The build gate requires `bun@^1.3.14` (`packages/script`); CI pins
  1.3.14. Keep the pre-push hook's check in sync with it.
- Local newer bun lives at `/tmp/opencode/bun-dir` (installed with
  `BUN_INSTALL` override; system bun untouched — this container *is* a
  running opencode session).

## 9. Contract-change ripples (the first CI run)

CI failed 7 tests, all contract drift from F0 — none upstream:

- 4 × ShareNext: tests need `OPENCODE_ENABLE_SHARE` (§3).
- config "account config with account token": tested the removed console
  config fetch; deleted with the feature.
- help-text snapshot: listed the deleted `upgrade` command, and its root
  entry predated the ASCII banner CI renders. Regenerated with `-u`.
- `httpapi-listen` "no Effect HTTP response logs": probed `/status`,
  which used to ride the `app.opencode.ai` proxy to a 200; now it falls
  to the UI fallback (503 by design). Probes `/doc` (a real 200 API
  route) instead — the test is about stderr noise, not routing.

General lesson: removing a proxy/fallback changes every test that used
the fallback as a convenient 200. Grep the tests for the removed
behavior, not just the source.

One CI-only flake remains understood, not fixed:
`run-process.test.ts` asserts `durationMs < 15_000` on a subprocess cold
start; with both CI jobs installing 2,669 packages on one runner it can
exceed the bound (local run of the same commit: 13/13 in 37 s). Rerun
clears it; a durable fix would relax the bound or split the jobs.

## 10. Snapshot regeneration semantics

`bun test -u` rewrote 205 lines for one logical change because the whole
root-help entry (banner included) re-serialized. Read the diff before
trusting it: the expected delta is removed commands plus banner text —
anything else means the local render differs from CI's (TTY/color
sensitivity) and needs a forcing env in the test.

## 11. The compliance bot governs from main

PR events execute workflow files from the **merge ref**, but scheduled
workflows (`compliance-close.yml`, 30-minute cron) execute from the
default branch. Deleting the bot workflows on the PR branch does not
stop the cron — `main` itself had to be trimmed (`4ed6928`, direct
push). The bot (`github-actions[bot]`, `pr-standards.yml` +
`compliance-close.yml`) had auto-flagged the F0 PR for missing template
sections against upstream's dev-branch CONTRIBUTING rules. Fix was two
sided: satisfy the template in the PR body, and delete the fleet on
`main`. `main` now carries only `ci.yml` + `release.yml`, identical to
the branch, so the merge diff stays clean.

## 12. Auth: the persistence gap

`?auth_token=` (base64 basic auth) was decoded at startup and merged
into the server list for display — but nothing wrote it to the persisted
`server.v3` store, and `server.add()` is user-initiated only. After
`clearAuthToken()` stripped the URL, reload booted without credentials
(401s). `reconcileStartupCredentials` folds credential-carrying startup
servers into the store once at provider init: adds missing entries,
upgrades url-only entries, no-ops when credentials match or are absent.
Four tests pin the matrix. The resolveServerList tests already covered
the *display* merge — persistence was the untested half.

## 13. Classifying CI failures (method that worked)

1. Pull the exact `(fail)` lines (`gh run view --log-failed`), not the
   grouped file list — bun's `--only-failures` output shows error *prints
   inside passing tests* as groups (attention, plugin-loader, acp, llm
   looked scary; none were failures).
2. For each: could the commit delta touch it? Run the file locally at the
   pushed commit with the CI bun version.
3. If it fails locally too: `git stash -u`, run at clean HEAD, compare —
   that separated the cf-ai-gateway failures (fail on clean HEAD locally,
   pass on the CI runner → live-endpoint tests, environment-dependent,
   leave alone) from real drift.

## 15. The opentui declarations class (next blocker)

After the drizzle fix, `packages/opencode` typecheck shows 151 errors —
zero drizzle, all one class: `@opentui/core` resolves to its
declaration-less `index.node.js` (TS7016 → `any` cascade in tui sources
and tui-adjacent tests). Present in `packages/tui`'s own typecheck too
(115 errors), so it is inherited and independent of F0. The package's
exports map declares `types: ./index.d.ts` first, yet tsgo picks the
node entry — suspected tsgo (native-preview) exports-condition handling
under `@tsconfig/bun`. This is what still blocks root
`bun turbo typecheck` and clean pre-push.
